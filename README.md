# NoSQL Java Guide

Учебный репозиторий по NoSQL для backend-разработчика на Java. Здесь есть углублённая
теория (как устроены Redis, MongoDB и Cassandra изнутри: репликация, партиционирование,
модели согласованности, движки хранения) и практические задания на реальных кейсах —
с автоматической проверкой через тесты, а не «на глаз».

**Для кого.** Уровень — от junior+ и выше: базовый Java и SQL нужны, опыт с NoSQL — нет.
Если вы никогда не работали ни с одной NoSQL-СУБД, это нормальная стартовая точка.

## Стек и версии

- **Java 21**, сборка только через Maven Wrapper (`./mvnw`, `mvnw.cmd`).
- Parent-POM: `org.springframework.boot:spring-boot-starter-parent:4.1.1`. Версии
  зависимостей (Testcontainers, драйверы, JUnit) фиксирует BOM из parent, отдельно в
  модулях не указываются.
- Драйверы: Lettuce (Redis), MongoDB Java Driver, DataStax Java Driver (Cassandra).
- Тесты: JUnit 5, AssertJ, Testcontainers, Awaitility.
- Docker-образы СУБД: `redis:8.2`, `mongo:8.0`, `cassandra:5.0`.
- Язык: теория и тексты заданий — русский; код и идентификаторы — английский;
  комментарии в коде — русский.

## Требования

- **JDK 21** — сборка проверяет версию Java и остановится с понятной ошибкой, если она
  ниже 21.
- **Docker** (Desktop или Engine) — под него нужно **не меньше 6 GB RAM**, иначе Cassandra
  и MongoDB в контейнерах могут падать или зависать. Docker нужен для:
  - `docker compose up -d` — поднимает Redis, MongoDB и Cassandra локально одной командой,
    чтобы поработать с ними руками (`redis-cli`, `mongosh`, `cqlsh`);
  - **Testcontainers** — библиотеки, которую используют тесты: она сама поднимает
    настоящий Redis/MongoDB/Cassandra в контейнере на время теста и убирает его после.
    Тесты проверяют код на реальной СУБД, а не на моках, поэтому Docker должен быть
    запущен и для `./mvnw verify`, а не только для `docker compose up`.

### JAVA_HOME на разных системах

На части машин `JAVA_HOME` по умолчанию указывает на старую версию JDK (например, 11).
Если сборка ругается на версию Java, задайте `JAVA_HOME` на JDK 21 для одной команды,
не трогая системные переменные:

**Git Bash (Windows):**
```bash
JAVA_HOME="C:/Users/<вы>/.jdks/temurin-21.0.9" ./mvnw verify
```

**PowerShell (Windows):**
```powershell
$env:JAVA_HOME = "C:\Users\<вы>\.jdks\temurin-21.0.9"
.\mvnw.cmd verify
```

**Linux / macOS:**
```bash
JAVA_HOME=/path/to/jdk-21 ./mvnw verify
```

В cmd.exe и PowerShell используйте `mvnw.cmd` вместо `./mvnw` — это тот же Maven Wrapper,
но для Windows.

## Быстрый старт

```bash
./mvnw verify                                             # проверить, что всё собирается
docker compose up -d                                      # СУБД для экспериментов
./mvnw -Ptasks -pl redis/tasks test -Dtest=RateLimiterTest # решить задание (пример; заработает, когда появится раздел Redis)
./mvnw verify -Dgroups=slow -DexcludedGroups=             # медленные тесты (кластер Cassandra)
```

Строка с `RateLimiterTest` — пример на будущее: модуль `redis/tasks` появится вместе с
разделом Redis (план 2), до этого команда завершится ошибкой
`Could not find the selected project in the reactor: redis/tasks`.

- `./mvnw verify` без флагов собирает `examples` и `solutions`: зелёная сборка означает,
  что весь материал репозитория рабочий. Сейчас модули СУБД ещё добавляются, поэтому
  `verify` проверяет только скелет репозитория (без Redis/MongoDB/Cassandra).
- `docker compose up -d` понадобится, только если хотите повозиться с СУБД руками —
  тестам он не нужен, они запускают контейнеры сами через Testcontainers.
- Профиль `-Ptasks` подключает модули с заданиями для студента (по умолчанию их нет в
  сборке, чтобы `./mvnw verify` не падал на нерешённых заданиях). Пока модули СУБД не
  добавлены, профиль не подключает ничего.
- Медленные тесты (например, кластер Cassandra из нескольких нод) по умолчанию
  отключены и помечены `@Tag("slow")`; команда выше включает их явно.

## Как устроены задания

Каждое задание — это пара модулей с одинаковыми именами классов:

- **`tasks`** — заготовка: методы с `TODO` внутри (`throw new UnsupportedOperationException`)
  и тесты, которые должны стать зелёными после того, как вы допишете код.
- **`solutions`** — эталонное решение с теми же классами и теми же тестами.

Совет: не подглядывайте в `solutions`, пока тесты в `tasks` не позеленеют сами. Смысл
задания — прийти к рабочему решению через тесты, а эталон нужен, чтобы свериться или
разобраться, если совсем застряли.

У каждого задания есть README с бизнес-контекстом, требованиями и подсказками —
он лежит рядом с заготовкой (`<db>/tasks/NN-<name>.md`).

## Порядок изучения

1. **[00. Общая теория](docs/00-foundations/README.md)** — без неё материал по конкретным
   СУБД читается как набор «магических» настроек.
2. **Redis** → **MongoDB** → **Cassandra** — порядок между ними не принципиален, но так
   заложена нарастающая сложность заданий.
3. **Сравнение** — обобщающий раздел и итоговое задание на архитектуру.

## Про порты

`docker compose up -d` занимает стандартные порты СУБД: `6379` (Redis), `27017`
(MongoDB), `9042` (Cassandra). Если порт уже занят другим контейнером или процессом:

- остановите то, что его занимает, либо
- поменяйте **левую** часть маппинга портов в `docker-compose.yml` (например,
  `"16379:6379"`), не трогая правую — это порт внутри контейнера.

На тесты это не влияет: Testcontainers сам подбирает свободные порты и не зависит от
`docker-compose.yml`.

## Подключение к СУБД из docker-compose

После `docker compose up -d` СУБД доступны локально по стандартным портам:

- **Redis**: `redis://localhost:6379`
- **MongoDB**: `mongodb://localhost:27017/?replicaSet=rs0&directConnection=true`
- **Cassandra**: `localhost:9042`, локальный дата-центр (local datacenter) — `datacenter1`
  (нужен для `LOCAL_QUORUM`/`LOCAL_SERIAL` и настройки драйвера DataStax).
