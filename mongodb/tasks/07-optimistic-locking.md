# Задание 07. Оптимистическая блокировка через version   ★★

**Бизнес-контекст:** в приложении пользователь редактирует свой профиль: имя и «о себе». Профиль открыт сразу на
телефоне и в браузере, а ещё его иногда правит служба поддержки. Типичная беда: оба клиента прочитали профиль,
каждый внёс свою правку и записал документ целиком, так что запись одного молча затёрла правку другого. Блокировать
строку на время редактирования нельзя: человек может уйти пить чай на полчаса. Нужен оптимистический подход:
пишем только если документ не менялся с момента чтения, а при конфликте честно сообщаем об этом или повторяем
правку заново.

## Что нужно сделать

- Коллекция `t07_profiles`: `{_id: String id, displayName: String, bio: String, version: long}`.
- Новый профиль создаётся с `version` 0 и пустым `bio`. Дубликат `id` не обрабатывается: исключение драйвера
  (`MongoWriteException` с кодом 11000) уходит вызывающему как есть.
- Правка проверяет версию и пишет данные одной операцией над одним документом, без транзакции: фильтр
  `{_id, version: expected}`, изменение `$set` полей и `$inc` версии на 1, в ответе документ уже после правки.
- Если операция ничего не нашла, нужно понять почему: профиля нет вообще (`NoSuchElementException`) или версия
  в базе уже другая (`StaleVersionException` с ожидаемой и фактической версиями).
- Правка с повтором: прочитать профиль, применить функцию изменения, записать с прочитанной версией. При
  `StaleVersionException` повторить с чтения. Попыток не больше `maxAttempts` (при `maxAttempts < 1` — `IllegalArgumentException`); если все исчерпаны, пробросить
  последнее `StaleVersionException`. Если профиля нет, `updateWithRetry` пробрасывает `NoSuchElementException`.
- Модели в коде собираются из `org.bson.Document` вручную.

## API

```java
public final class Profiles {
    public Profiles(MongoDatabase database);

    public void create(String id, String displayName);
    public Optional<Profile> get(String id);
    public Profile update(String id, long expectedVersion, String displayName, String bio);
    public Profile updateWithRetry(String id, UnaryOperator<Profile> change, int maxAttempts);
}

public record Profile(String id, String displayName, String bio, long version) {}

public final class StaleVersionException extends RuntimeException {
    public StaleVersionException(String id, long expected, long actual);
    public long expected();
    public long actual();
}
```

- `create` создаёт профиль с версией 0 и пустым `bio`.
- `get` возвращает профиль или пустой `Optional`.
- `update` меняет `displayName` и `bio`, увеличивает версию на 1 и возвращает новое состояние профиля.
- `updateWithRetry` передаёт в `change` свежепрочитанный профиль; из результата берутся `displayName` и `bio`,
  версия берётся из прочитанного профиля.

`Profile` и `StaleVersionException` даны готовыми, менять их не нужно. Ваша часть — `Profiles`.

## Как проверить

```bash
bash scripts/mvn-docker.sh -Ptasks -pl mongodb/tasks test -Dtest='dev.nosqlguide.mongodb.tasks.task07.*Test'
```

Эталон:

```bash
bash scripts/mvn-docker.sh -pl mongodb/solutions test -Dtest='dev.nosqlguide.mongodb.tasks.task07.*Test'
```

- `updateIncrementsVersion` — после правки версия 1, поля обновлены, `get` возвращает то же состояние.
- `staleVersionIsRejectedWithActual` — две правки с версией 0: вторая даёт `StaleVersionException` (ожидалась 0, в базе 1), данные первой правки на месте.
- `missingProfileThrowsNoSuchElement` — правка несуществующего профиля даёт `NoSuchElementException`, `get` возвращает пустой `Optional`.
- `duplicateCreateFails` — повторный `create` с тем же `id` даёт `MongoWriteException` с кодом 11000, старый профиль не тронут.
- `concurrentRetriesApplyEveryChange` — 8 потоков одновременно дописывают в `bio` каждый свою букву через `updateWithRetry` (до 50 попыток): в `bio` все 8 букв, версия 8.
- `retriesExhaustedThrows` — функция изменения сама двигает версию сторонним `update`, поэтому все 3 попытки устаревают: `StaleVersionException`, функция вызвана ровно 3 раза.

## Подсказки

<details>
<summary>1. Идея оптимистической блокировки</summary>

Не держим блокировку, пока человек думает. Вместе с данными храним счётчик версии. Пишем только при условии, что
версия в базе всё ещё та, что мы прочитали, и при каждой записи увеличиваем её. Если условие не выполнилось,
кто-то нас опередил, и решать, что делать, должен вызывающий код.
</details>

<details>
<summary>2. Почему здесь не нужна транзакция</summary>

Проверка версии и запись должны быть неделимыми. Операции над одним документом в MongoDB атомарны сами по себе,
подробнее в разделе об [атомарности одного документа](../theory/01-document-bson.md#атомарность-одного-документа).
Когда транзакция всё же нужна и сколько она стоит, описано в главе про [транзакции](../theory/08-transactions.md).
</details>

<details>
<summary>3. Одно обращение вместо «прочитать, сравнить, записать»</summary>

Если сравнить версию в приложении, а потом записать, между этими шагами может вклиниться чужая запись. Условие
вынесите в фильтр операции «найти и обновить», а возвращаемый документ настройте так, чтобы приходило состояние
после правки. Пустой результат означает, что фильтр ничего не нашёл.
</details>

<details>
<summary>4. Почему фильтр не нашёл документ</summary>

У пустого результата две причины: документа нет или версия другая. Различить их можно только дополнительным
чтением. Эта проверка уже не влияет на корректность: запись не произошла в любом случае, чтение нужно лишь для
понятного сообщения об ошибке.
</details>

<details>
<summary>5. Цикл повторов</summary>

Каждая попытка начинается с нового чтения, иначе вы будете снова и снова писать с той же устаревшей версией.
Запоминайте последнее исключение, чтобы вернуть его, когда попытки кончатся. Функция изменения может
вызываться несколько раз, поэтому она должна быть чистой, без побочных эффектов.
</details>

## Подумайте после решения

- Чем `replaceOne` с фильтром по версии хуже `$set` + `$inc`? Что произойдёт с полями, которые добавила другая
  версия приложения, и что нужно делать с версией внутри заменяемого документа?
- Почему при конфликте в `updateWithRetry` нельзя просто повторить `update` с той же версией? Чем автоматический
  повтор опасен, если функция изменения зависит от того, что пользователь увидел на экране?
- Как поведёт себя схема при очень горячем документе, который правят десятки клиентов одновременно? Сколько
  попыток понадобится в худшем случае и чем это лучше или хуже пессимистической блокировки?
- В каких случаях вместо версии лучше обойтись атомарным оператором вроде `$inc` или `$push` без чтения?
