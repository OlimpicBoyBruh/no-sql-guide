# Задание 04. Пагинация комментариев: keyset против skip, subset pattern ★★

**Бизнес-контекст:** в блоге у популярных постов десятки тысяч комментариев. Страница поста показывает три
последних комментария и счётчик, а кнопка «Показать ещё» подгружает остальные порциями. Сейчас на каждый показ
поста приложение читает комментарии отдельным запросом, а «Показать ещё» сделана через `skip`: на глубоких
страницах база долго отбрасывает сотни тысяч записей, а если пока пользователь читает, пришёл новый комментарий,
на следующей странице он видит повтор. Нужно хранить свежие комментарии прямо в документе поста и листать
остальные по курсору.

## Что нужно сделать

- Коллекция `t04_posts`: `{_id: String postId, title: String, commentCount: int, recentComments: [до 3 последних]}`.
  Элементы `recentComments` — полные копии комментариев (`_id`, `postId`, `createdAt`, `author`, `text`).
- Коллекция `t04_comments`: `{_id: ObjectId, postId: String, createdAt: Date, author: String, text: String}`.
- Порядок комментариев везде один: `createdAt` по убыванию, при равном времени `_id` по убыванию.
- Добавление комментария: вставка в `t04_comments` и обновление поста одним `updateOne`: увеличить `commentCount`
  и добавить комментарий в `recentComments` так, чтобы там остались только `RECENT` самых новых по тому же порядку.
  Транзакция не нужна.
- Страницы листаются по курсору (keyset): следующая страница начинается строго после последнего показанного
  комментария, смещения (`skip`) в `page` нет.
- Индекс `t04_comments` на `{postId: 1, createdAt: -1, _id: -1}` создаёт `ensureIndexes()`.
- Документы в record'ы превращайте вручную через `org.bson.Document`. Время хранится как `Date` (миллисекунды).

## API

```java
public final class Comments {
    public static final int RECENT = 3;

    public Comments(MongoDatabase database);

    public void ensureIndexes();
    public void createPost(String postId, String title);
    public ObjectId add(String postId, Instant createdAt, String author, String text);
    public PostView post(String postId);
    public CommentPage page(String postId, int size, String cursor);
    public List<Comment> pageBySkip(String postId, int pageNumber, int size);
}

public record Comment(ObjectId id, String postId, Instant createdAt, String author, String text) {}
public record CommentPage(List<Comment> comments, String nextCursor) {}
public record PostView(String postId, String title, int commentCount, List<Comment> recentComments) {}
```

- `createPost` создаёт пост со счётчиком `0` и пустым списком последних комментариев.
- `add` возвращает `_id` созданного комментария. Комментарий может прийти «задним числом» (с `createdAt` раньше
  уже существующих), `recentComments` всё равно должен содержать три самых новых по порядку выдачи.
- `post` возвращает пост с последними комментариями в порядке выдачи (новые первыми). Если поста нет,
  бросает `NoSuchElementException`.
- `page` при `cursor == null` отдаёт первую страницу. Читайте `size + 1` записей: лишняя говорит, что следующая
  страница есть, и в ответ она не попадает. `nextCursor` — курсор последнего возвращённого комментария,
  а на последней странице `null`. Формат курсора выбираете сами, снаружи это непрозрачная строка.
  Строку, которую нельзя разобрать, `page` отвергает с `IllegalArgumentException`.
- `pageBySkip` нужен только для сравнения: страница с номером `pageNumber` (с нуля) через `skip`/`limit` в том же порядке.

`Comment`, `CommentPage` и `PostView` даны готовыми, менять не нужно. Ваша часть — `Comments`.


Эталон:

```bash
bash scripts/mvn-docker.sh -pl mongodb/solutions test -Dtest='dev.nosqlguide.mongodb.tasks.task04.*Test'
```

- `subsetKeepsThreeNewest` — после пяти комментариев (вставленных не по порядку времени) в посте ровно три самых новых по порядку, а `commentCount` равен 5.
- `keysetPagesWalkAllWithoutGaps` — семь комментариев при `size` 3 дают страницы 3, 3, 1, у последней `nextCursor == null`, а склейка страниц — все семь по порядку.
- `exactMultipleHasNullCursorOnLastPage` — шесть комментариев при `size` 3: вторая страница заполнена полностью и всё равно имеет `nextCursor == null`.
- `tieOnCreatedAtAcrossPageBoundary` — два комментария с одинаковым `createdAt` разделены границей страницы: ни потерь, ни повторов, порядок внутри ничьей по `_id` по убыванию.
- `newCommentDoesNotShiftKeysetButShiftsSkip` — после добавления нового комментария вторая страница keyset не повторяет первую, а `pageBySkip` повторяет её последний элемент. Тест намеренно проверяет именно этот дефект `skip`, он не ошибка в вашем коде.
- `invalidCursorIsRejected` — мусорные строки в качестве курсора дают `IllegalArgumentException`, а не `NullPointerException` или ошибку драйвера.
- `missingPostThrows` — `post("nope")` бросает `NoSuchElementException`.

## Подсказки

<details>
<summary>1. Зачем хранить копию последних комментариев в посте</summary>

Чтобы показать пост с тремя свежими комментариями, не нужен второй запрос: они лежат рядом со счётчиком.
Этот приём называется subset pattern: в документе держат только ту часть связанных данных, которая нужна при
каждом чтении, а остальное остаётся в отдельной коллекции. Цена — дублирование и две записи на каждое добавление;
подробности в разделе про [моделирование данных](../theory/03-data-modeling.md) (subset pattern).
</details>

<details>
<summary>2. Массив ограниченного размера одним обновлением</summary>

Оператор добавления в массив умеет не только дописывать элементы, но и упорядочивать массив после добавления
и обрезать его до заданной длины. Подумайте, как с его помощью получить «только N самых новых» без чтения
документа в приложение, и как задать порядок по двум полям сразу.
</details>

<details>
<summary>3. Курсор из двух значений</summary>

Если сортировка идёт по двум полям, то «позиция» записи — пара значений, а не одно. Условие «строго после
позиции» для пары записывается как «первое поле меньше, ИЛИ первое равно, а второе меньше». Какие именно
значения нужно упаковать в курсор и как превратить их в строку и обратно, решаете вы; следите за тем, чтобы
любой мусор на входе превращался в одно предсказуемое исключение. Как индекс помогает такому запросу, —
в главе про [индексы](../theory/04-indexes.md#составной-индекс-и-правило-esr).
</details>

<details>
<summary>4. Откуда берётся «есть ли следующая страница»</summary>

Запрашивать общее число записей ради этого вопроса дорого и ненадёжно. Достаточно попросить у базы на одну запись
больше, чем помещается на страницу: если она пришла, следующая страница существует, а курсор строится по
последней записи, которая в ответ ещё входит.
</details>

## Подумайте после решения

- Во что обойдётся `skip(100000)` для базы, даже если `limit` равен 10? Почему время ответа растёт с номером страницы, а у keyset остаётся постоянным?
- Почему курсор по одному `createdAt` теряет записи? Что произойдёт, если на границе страниц у нескольких комментариев одно и то же время?
- Что увидит читатель между вставкой комментария и обновлением поста, если эти две записи идут без транзакции? Допустимо ли это для счётчика комментариев, а для остатка на счёте?
- Чего не умеет keyset-пагинация по сравнению с `skip` (например, прыжок на страницу 50) и как продукт обычно с этим живёт?
