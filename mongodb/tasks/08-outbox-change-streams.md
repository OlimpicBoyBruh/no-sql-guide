# Задание 08. Outbox и Change Streams с resume token   ★★★

**Бизнес-контекст:** после оформления заказа о нём должны узнать биллинг (выставить счёт) и склад (собрать
посылку). Если сервис заказов сначала пишет заказ в базу, а потом отправляет сообщение, то при падении между
этими шагами заказ есть, а счёта нет; если наоборот, счёт может уйти на заказ, который так и не сохранился.
Паттерн transactional outbox решает это так: событие пишется в отдельную коллекцию в той же транзакции, что и
заказ, а отдельный «ретранслятор» читает новые события через Change Stream и отдаёт потребителям. Ретранслятор
перезапускают при каждом деплое, по несколько раз в день, и ни одно событие при этом не должно потеряться.

## Что нужно сделать

- Коллекция `t08_orders`: `{_id: ObjectId, customerId: String, totalCents: long}`.
- Коллекция `t08_outbox`: `{_id: ObjectId, type: "OrderPlaced", aggregateId: String (hex id заказа),
  payload: {customerId, totalCents}, createdAt: Date}`.
- Коллекция `t08_offsets`: `{_id: String consumerName, resumeToken: Document}`, сохранённая позиция каждого
  потребителя в потоке изменений.
- `placeOrder` вставляет заказ и событие одной транзакцией (`ReadConcern.SNAPSHOT`, `WriteConcern.MAJORITY`,
  `ReadPreference.primary()`, как в задании 05). `totalCents <= 0` отвергается через `IllegalArgumentException`
  до начала транзакции.
- `init` ничего не делает, если у потребителя уже есть сохранённый токен. Если токена нет, он открывает поток
  изменений на `t08_outbox`, берёт текущий resume token (позицию «сейчас») и сохраняет его в `t08_offsets`.
- `poll` открывает поток на `t08_outbox` с конвейером `$match` по `operationType: "insert"`, продолжает
  с сохранённого токена (`resumeAfter`) и ждёт событий через `tryNext()` с `maxAwaitTime` не больше 500 мс.
  Цикл идёт, пока не набрано `max` событий или не истёк `maxWait`.
- После каждого полученного события `poll` сохраняет (upsert) токен курсора в `t08_offsets`. Курсор закрывается
  в `try-with-resources`.
- Если после того, как часть событий уже собрана (и их токены сохранены), запись токена или очередной `tryNext()`
  бросили исключение, `poll` возвращает собранное, а не теряет его. Исключение пробрасывается, только если не
  собрано ни одного события.
- `poll` без сохранённого токена (не вызывали `init`) бросает `IllegalStateException`.
- Документы событий собираются в `OutboxEvent` из `org.bson.Document` вручную.

## API

```java
public final class OrderService {
    public OrderService(MongoClient client, MongoDatabase database);

    public ObjectId placeOrder(String customerId, long totalCents);
}

public final class OutboxRelay {
    public OutboxRelay(MongoDatabase database, String consumerName);

    public void init();
    public List<OutboxEvent> poll(int max, Duration maxWait);
}

public record OutboxEvent(ObjectId id, String type, String aggregateId, Document payload) {}
```

- `placeOrder` возвращает `_id` заказа; `aggregateId` события равен его hex-строке.
- `OutboxRelay` хранит позицию под именем `consumerName`: у каждого потребителя своя, и они не мешают друг другу.
  Новый экземпляр с тем же именем продолжает с того места, где остановился прежний.
- `poll` возвращает события в порядке коммита, не больше `max`, и не ждёт заметно дольше `maxWait`.
  Пустой список означает «за это время новых событий не было».

`OutboxEvent` дан готовым, менять его не нужно. Ваша часть — `OrderService` и `OutboxRelay`.

**Про гарантии доставки.** Этот API фиксирует позицию (токен) внутри `poll`, то есть *до того*, как вызывающий
обработал события. Ретранслятор сам по себе событий не теряет (пока позиция в окне oplog): всё, что закоммичено после `init`, рано или поздно
вернёт какой-нибудь `poll`, и перезапуск продолжает с сохранённого места. Но с точки зрения потребителя
гарантия — «не больше одного раза»: если процесс упал после возврата из `poll`, но до обработки событий, позиция
уже сдвинута, и эти события он больше не увидит. Чтобы получить «хотя бы раз», позицию нужно фиксировать
*после* обработки: например, передавать в ретранслятор обработчик и сохранять токен, когда обработчик вернул
управление, или подтверждать (ack) каждое событие отдельным вызовом. Тогда падение во время обработки приводит
к повтору события, и потребитель должен уметь распознать уже обработанное (например, по `id`).

## Как проверить

```bash
bash scripts/mvn-docker.sh -Ptasks -pl mongodb/tasks test -Dtest='dev.nosqlguide.mongodb.tasks.task08.*Test'
```

Эталон:

```bash
bash scripts/mvn-docker.sh -pl mongodb/solutions test -Dtest='dev.nosqlguide.mongodb.tasks.task08.*Test'
```

Тесты используют replica set из одного узла: Change Streams и транзакции без него не работают. Тесты, которые
читают события через `OutboxRelay`, вызывают `init()` до первого заказа.

- `placedOrderProducesOneEvent` — заказ и ровно одно событие существуют, `aggregateId` равен id заказа, `payload.totalCents` совпадает, `poll` отдаёт это событие.
- `nonPositiveTotalRejected` — `totalCents` 0 и отрицательный дают `IllegalArgumentException`, ни заказа, ни события нет.
- `pollReturnsEventsInCommitOrder` — три заказа, `poll(10, 5 с)` возвращает три события в порядке заказов.
- `maxLimitsBatchAndNextPollContinues` — три заказа: `poll(1, …)` отдаёт первое, следующий `poll` два оставшихся, третий пуст.
- `restartResumesWithoutLossOrDuplicates` — потребитель прочитал два события; пока он «лежит», появились ещё два заказа; новый экземпляр с тем же именем после `init()` отдаёт ровно два новых и ничего больше.
- `consumersAreIndependent` — два потребителя с разными именами получают одни и те же события, у каждого своя запись в `t08_offsets`.
- `emptyPollReturnsWithinMaxWait` — без заказов `poll(10, 1 с)` возвращает пустой список быстрее чем за 2 секунды.
- `pollWithoutInitFails` — `poll` без `init` бросает `IllegalStateException`.

## Подсказки

<details>
<summary>1. Зачем outbox, если есть транзакция</summary>

Транзакция MongoDB охватывает только записи в эту базу; отправку сообщения в брокер в неё не включить. Поэтому
событие записывается рядом с заказом, тем же коммитом, а доставка вынесена в отдельный процесс. Тело транзакции
может выполниться несколько раз, а коммит может не состояться: что из этого следует для побочных эффектов,
разобрано в главе про [транзакции](../theory/08-transactions.md).
</details>

<details>
<summary>2. Что видит Change Stream</summary>

Поток изменений строится по oplog и показывает только закоммиченные изменения, причём записи одной транзакции
появляются после её коммита и в порядке коммитов. Как открыть поток из Java, отфильтровать нужные операции
конвейером и получить вставленный документ из события, описано в главе про
[Change Streams в Java](../theory/10-change-streams-java.md).
</details>

<details>
<summary>3. Курсор, который не блокирует навсегда</summary>

Обычный перебор курсора потока ждёт следующего события сколько угодно. Вам нужен метод, который ждёт не дольше
заданного времени и возвращает «ничего нет», если событий не появилось. Сколько ждёт один такой вызов, задаётся
при открытии потока; сделайте это время меньше `maxWait` и проверяйте общий дедлайн в цикле сами.
</details>

<details>
<summary>4. Где взять resume token</summary>

У курсора потока есть метод, возвращающий токен последней прочитанной позиции, а после пустой порции —
позицию, до которой сервер уже просмотрел oplog. Обратите внимание: на только что открытом курсоре, до первого
обращения за данными, драйвер этого проекта возвращает `null`. Подумайте, какое обращение к курсору безопасно
сделать в `init`, чтобы получить позицию «сейчас». Токен непрозрачен: храните его как документ, ничего в нём
не разбирая.
</details>

<details>
<summary>5. Когда сохранять токен</summary>

Условие требует сохранять токен внутри `poll`, после каждого полученного события. Подумайте, в каком порядке
сохранять токен и добавлять событие в результат, чтобы всё возвращённое было уже отмечено как прочитанное, и что
делать с собранными событиями, если следующая операция бросила исключение. И должен ли повторный `init` трогать
уже сохранённую позицию?
</details>

## Подумайте после решения

- Resume token указывает на запись в oplog, а oplog — ограниченная по размеру коллекция. Что произойдёт, если
  ретранслятор простоял дольше, чем [окно oplog](../theory/06-replica-set.md#размер-и-окно-oplog), и сохранённая
  позиция уже вытеснена? Какую ошибку получит `poll` и как из такой ситуации выбираться, имея под рукой саму
  коллекцию `t08_outbox`? Эталон сдвигает токен только на полученных событиях; что изменится, если после
  пустого `poll` сохранять и post-batch resume token, который сервер присылает даже без событий?
- Этот API фиксирует позицию до обработки, поэтому для потребителя доставка «не больше одного раза». Как
  изменить API (обработчик-колбэк или подтверждение каждого события), чтобы получить «хотя бы раз»? Что тогда
  должен делать потребитель, получив событие повторно, и почему проверка по `id` события надёжнее проверки по
  времени `createdAt`?
- `init` берёт позицию «сейчас». Событие, закоммиченное, пока `init` открывал поток, считается случившимся
  «до старта» потребителя и не будет ему доставлено. Почему повторный вызов `init` или исключение эту проблему
  не решили бы, и как начать чтение с гарантированно известной точки, если терять нельзя ничего?
- Коллекция `t08_outbox` только растёт. Как бы вы её чистили, не ломая потребителей, которые ещё не дочитали
  поток? Подойдёт ли TTL-индекс по `createdAt`?
