# Задание 03. Аналитика заказов: `$group`, `$facet`, `$lookup` ★★

**Бизнес-контекст:** маркетологам интернет-магазина каждое утро нужна сводка за месяц: сколько денег принесли
заказы по городам и как выглядит «пульс» магазина: сколько заказов в каждом статусе, какие три товара продаются
лучше всех и какова общая выручка. Сейчас сводку собирает скрипт, который тянет в приложение миллионы заказов
и считает всё в цикле, это занимает минуты и съедает память. Пусть считает сама база: один конвейер
агрегации на запрос, а в приложение приходят только готовые строки отчёта.

## Что нужно сделать

- Коллекция `t03_customers`: `{_id: String customerId, name: String, city: String}`.
- Коллекция `t03_orders`: `{_id, customerId: String, status: "paid" | "cancelled" | "new", createdAt: Date, items: [{sku: String, qty: int, priceCents: long}]}`.
- Период задаётся полуинтервалом `[from, toExclusive)`: заказ ровно в `toExclusive` в него не входит.
- Выручка заказа = сумма `qty × priceCents` по всем позициям. Деньги — `long` в центах.
- Весь подсчёт выполняет база в конвейере `aggregate`; читать заказы в Java и суммировать там нельзя.
- Документы в record'ы превращайте вручную через `org.bson.Document`.

## API

```java
public final class OrderAnalytics {
    public static final String CUSTOMERS = "t03_customers";
    public static final String ORDERS = "t03_orders";

    public OrderAnalytics(MongoDatabase database);

    public List<RevenueByCity> revenueByCity(Instant from, Instant toExclusive);
    public Dashboard dashboard(Instant from, Instant toExclusive);
}

public record RevenueByCity(String city, long revenueCents, int orders) {}
public record SkuQty(String sku, long qty) {}
public record Dashboard(Map<String, Integer> ordersByStatus, List<SkuQty> topSkus, long paidRevenueCents) {}
```

- `revenueByCity` учитывает только заказы со статусом `paid` из периода. Первой стадией конвейера идёт `$match`.
  Город берётся из `t03_customers` через `$lookup`; если клиента в справочнике нет, город равен `"unknown"`.
  Результат отсортирован по выручке по убыванию, при равной выручке по городу по возрастанию.
- `dashboard` делает один вызов `aggregate` с `$facet` из трёх веток над заказами периода (всех статусов):
  число заказов по каждому статусу; три самых продаваемых SKU по суммарному `qty` среди `paid`
  (при равенстве `qty` раньше SKU, который идёт первым по алфавиту); суммарная выручка `paid`.
- В `ordersByStatus` попадают только статусы, которые встречаются в периоде. Нулевых записей нет.
  Если в периоде заказов нет, карта и список пусты, а выручка равна `0`.

`RevenueByCity`, `SkuQty` и `Dashboard` даны готовыми, менять их не нужно. Ваша часть — `OrderAnalytics`.

## Подсказки

<details>
<summary>1. Конвейер как цепочка стадий</summary>

Агрегация — это последовательность стадий: документы входят в первую, выходят из последней, и каждая стадия
получает результат предыдущей. Какие стадии бывают и как они комбинируются, — в главе
[«Агрегации»](../theory/05-aggregation.md).
</details>

<details>
<summary>2. Сначала отфильтруйте, потом соединяйте</summary>

Стадия соединения с другой коллекцией дорогая: она работает для каждого документа, дошедшего до неё. Подумайте,
какие заказы вам точно не нужны, и уберите их как можно раньше. От порядка стадий зависит и то, сможет ли база
воспользоваться индексом.
</details>

<details>
<summary>3. Выручка и группировка</summary>

Выручка заказа считается по массиву позиций внутри самого документа: в выражениях есть операторы, которые
обходят массив и складывают результаты, не разворачивая его в отдельные документы. А для группировки нужно
выбрать ключ группы и накопители: сумму выручки и количество заказов. Что делает `$lookup` с отсутствующим
совпадением и как подставить значение по умолчанию, — в [теории про `$lookup`](../theory/05-aggregation.md).
</details>

<details>
<summary>4. Три ветки в одном запросе</summary>

Стадия `$facet` запускает несколько независимых подконвейеров над одним и тем же набором входных документов
и возвращает результат каждого массивом под своим именем. Каждая ветка может начинаться со своего фильтра.
Подумайте, что вернёт ветка с группировкой, если на вход не пришло ни одного документа, и как с этим
справиться в Java.
</details>

## Подумайте после решения

- Почему `$match` должен стоять до `$lookup`, а не после? Что изменится по объёму работы, если период выбирает 1% заказов?
- Чем плох `$lookup` по большой коллекции, если по полю `foreignField` нет индекса? Сколько раз и как база будет обходить
  коллекцию клиентов?
- Почему `$facet` удобен для дашборда, но его подконвейеры не могут использовать индексы и вся входная выборка проходит через память?
  Когда лучше сделать три отдельных запроса?
- Что вернёт ветка `$facet` с `$group` без ключа на пустом входе, и почему в ветке по статусам такой проблемы нет?
