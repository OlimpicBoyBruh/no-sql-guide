# Задание 05. Оформление заказа в транзакции с повтором   ★★★

**Бизнес-контекст:** в интернет-магазине идёт распродажа: на складе осталось пять единиц хита продаж, а покупателей
в этот момент десятки. Заказ меняет сразу два места: уменьшает остаток товара и создаёт документ заказа. Если
сервис упал между этими шагами, склад «похудел», а заказа нет; если два покупателя одновременно прочитали остаток
«5» и оба списали по единице, в худшем случае продано больше, чем есть. Нужно оформлять заказ как одну
транзакцию и пережить конфликты, которые при этом неизбежно возникают.

## Что нужно сделать

- Коллекция `t05_inventory`: `{_id: String sku, available: int}`, остаток товара на складе.
- Коллекция `t05_orders`: `{_id: ObjectId, customerId: String, items: [{sku: String, qty: int}], status: "placed"}`.
- `placeOrder` выполняется одной транзакцией с параметрами: `ReadConcern.SNAPSHOT`, `WriteConcern.MAJORITY`,
  `ReadPreference.primary()`. Для транзакций они задаются в `TransactionOptions`.
- В теле транзакции для каждого SKU остаток уменьшается условным обновлением: документ подходит, только если
  `available` не меньше нужного количества. Если обновление не нашло подходящего документа, товара не хватает:
  бросьте `OutOfStockException` с этим SKU. Транзакция откатывается целиком, исключение уходит вызывающему.
- После списания всех позиций в той же сессии вставляется заказ со статусом `placed`.
- Повторы при конфликтах (`TransientTransactionError`) и неопределённом результате коммита
  (`UnknownTransactionCommitResult`) делает сам драйвер, свой цикл повторов писать не нужно.
- Пустой `items` или любое `qty <= 0` отвергаются через `IllegalArgumentException` до начала транзакции.
- Начиная с MongoDB 4.4 коллекцию можно создать прямо внутри транзакции (на `mongo:8.0` вставка в новую коллекцию с `ReadConcern.SNAPSHOT` проходит). Но тест создаёт обе коллекции заранее: так первые одновременные вставки не гоняются за создание коллекции и не дают лишних конфликтов.

## API

```java
public final class Checkout {
    public Checkout(MongoClient client, MongoDatabase database);

    public ObjectId placeOrder(String customerId, Map<String, Integer> items);
}

public final class OutOfStockException extends RuntimeException {
    public OutOfStockException(String sku);
    public String sku();
}
```

- `placeOrder` возвращает `_id` созданного заказа. `items` — SKU и количество; порядок обхода карты определяет
  порядок списания.
- `MongoClient` нужен, чтобы открыть `ClientSession`; коллекции берутся из `MongoDatabase`.

`OutOfStockException` дан готовым, менять не нужно. Ваша часть — `Checkout`.

Эталон:

```bash
bash scripts/mvn-docker.sh -pl mongodb/solutions test -Dtest='dev.nosqlguide.mongodb.tasks.task05.*Test'
```

- `successfulOrderDecrementsAndInserts` — после заказа остатки уменьшились, документ заказа есть, а его `items` совпадают с запрошенными.
- `outOfStockRollsBackEverything` — первого SKU хватает, второго нет: бросается `OutOfStockException` со вторым SKU, остаток первого не изменился, заказов нет.
- `concurrentBuyersNeverOversell` — остаток 5, десять потоков стартуют одновременно и покупают по одной штуке: ровно 5 успехов, 5 `OutOfStockException`, остаток 0, заказов 5; любое другое исключение провалит тест.
- `invalidItemsRejectedBeforeTransaction` — пустая карта и `qty = 0` дают `IllegalArgumentException`, заказов нет.

## Подсказки

<details>
<summary>1. Что такое транзакция в MongoDB и когда она нужна</summary>

Операции над одним документом атомарны и без транзакции. Транзакция нужна, когда «всё или ничего» должно
выполняться сразу для нескольких документов или коллекций, как здесь: склад и заказ. Как устроена многодокументная
транзакция и чем она дороже одиночной записи, описано в главе про [транзакции](../theory/08-transactions.md).
</details>

<details>
<summary>2. Сессия и тело транзакции</summary>

Транзакция живёт внутри сессии. У сессии есть метод, который принимает тело транзакции и параметры, сам начинает
транзакцию, коммитит её и повторяет при временных ошибках. Важное правило: каждая операция внутри тела должна
получать эту сессию явным аргументом, иначе она выполнится вне транзакции. Что произойдёт, если тело бросит
исключение, посмотрите в документации метода.
</details>

<details>
<summary>3. Уровни согласованности транзакции</summary>

Три настройки транзакции: что видит чтение (read concern), когда запись считается подтверждённой (write concern)
и откуда читать (read preference). Какие значения допустимы внутри транзакции и что они гарантируют, разобрано
в главе про [read и write concern](../theory/07-read-write-concerns.md). Параметры собираются в объект
настроек транзакции и передаются вместе с телом.
</details>

<details>
<summary>4. Как не уйти в минус</summary>

Подумайте, можно ли проверить остаток и списать его одним обращением к базе, а не двумя. Если условие
«достаточно товара» вынести в фильтр обновления, то по числу подошедших документов можно понять, получилось
ли списание. Тогда вопрос «хватило ли» решает сама база, а не код приложения, который мог прочитать устаревшее значение.
</details>
