# Задание 01. Кэш карточек товаров (cache-aside, TTL с jitter) ★

**Бизнес-контекст:** интернет-магазин показывает карточку товара (название, цена) миллионам
посетителей в сутки, а хранится она в основной БД, которая под пиковой нагрузкой отвечает
за десятки миллисекунд. Прямое чтение из БД на каждый показ карточки не выдержит трафик, поэтому
перед БД ставится кэш в Redis по классической схеме cache-aside: сервис сначала спрашивает кэш,
и только при промахе идёт в БД и заполняет кэш сам. Отдельная проблема — «лавина промахов»
(thundering herd): если у всех карточек, прогретых в одну секунду, будет и TTL с точностью
до секунды, они все одновременно протухнут и разом обрушат БД потоком одинаковых запросов.
Вторая проблема — «дырявые» id (опечатка, отменённый товар, перебор чужих id ботом): без защиты
каждый такой запрос идёт мимо кэша прямо в БД.

## Что нужно сделать

- Ключ `product:{id}`, тип **Hash**, поля `id`, `name`, `priceCents`.
- При промахе (в Redis ключа нет): загрузить товар из `ProductRepository`, записать в Redis как Hash
  и выставить TTL = `baseTtl + random(0..maxJitter)` (случайное значение равномерно распределено
  в миллисекундах между 0 и `maxJitter` включительно) — это и есть защита от лавины промахов.
- Если товара нет и в БД: negative caching — записать Hash с единственным полем `_missing` = `1`
  и TTL = `negativeTtl` (без jitter). Повторный `get` того же id должен вернуть `Optional.empty()`
  **не обращаясь к репозиторию** — это защита от «дырявых» id.
- `invalidate(id)` удаляет ключ из кэша целиком (например, вызывается после изменения цены в БД).
- Запись Hash и выставление TTL — одна атомарная операция на стороне Redis (Lua-скрипт `EVAL`, либо
  `MULTI/EXEC`, но обязательно на отдельном соединении, не на общем). Два отдельных вызова (сначала
  `HSET`, потом `PEXPIRE`) — риск «вечного» ключа: если процесс упадёт или связь с Redis оборвётся
  между двумя командами, `HSET` уже выполнится, а `PEXPIRE` — нет, и ключ останется в кэше без TTL
  навсегда, отдавая устаревшие данные бесконечно.

## API

```java
public final class ProductCache {
    public ProductCache(StatefulRedisConnection<String, String> connection,
                        ProductRepository repository,
                        Duration baseTtl,
                        Duration maxJitter,
                        Duration negativeTtl,
                        RandomGenerator random);

    /** Вернуть товар из кэша, а при промахе загрузить из репозитория и положить в кэш. */
    Optional<Product> get(String id);

    /** Удалить товар из кэша (например, после изменения цены). */
    void invalidate(String id);
}
```

`Product` — `record Product(String id, String name, long priceCents)`.
`ProductRepository` — интерфейс с одним методом `Optional<Product> findById(String id)`, ваша
«база данных» позади кэша.

## Как проверить

```
bash scripts/mvn-docker.sh -Ptasks -pl redis/tasks test -Dtest='dev.nosqlguide.redis.tasks.task01.*Test'
```

Почему через `scripts/mvn-docker.sh`, а не напрямую `./mvnw` — [redis/README.md, раздел «Как запускать тесты»](../README.md#как-запускать-тесты).

Тесты `ProductCacheTest`:
- `missLoadsFromRepositoryAndStoresHash` — при первом обращении товар грузится из репозитория и
  сохраняется в Redis-хэше с полями `id`/`name`/`priceCents`.
- `hitDoesNotCallRepository` — второй `get` того же id отдаётся из кэша, репозиторий не вызывается.
- `ttlIsBaseTtlPlusJitter` — TTL после записи лежит в диапазоне `[baseTtl, baseTtl + maxJitter]`.
- `jitterSpreadsExpirationOfDifferentKeys` — у 20 разных ключей, прогретых подряд, TTL в секундах
  не совпадают почти у всех (jitter действительно размазывает истечение по времени).
- `missingProductIsCachedNegatively` — отсутствующий в БД товар кэшируется негативно, повторный
  `get` не идёт в репозиторий, TTL записи не превышает `negativeTtl`.
- `invalidateRemovesEntry` — после `invalidate` ключ исчезает из Redis, следующий `get` снова идёт
  в репозиторий.

## Подсказки

<details>
<summary>1. С чего начать</summary>

`get` — это `HGETALL product:{id}`. Если Redis вернул пустой хэш — промах: идём в
`ProductRepository`, дальше по требованиям. Если хэш непустой — решаем, обычная это карточка
или запись негативного кэша (смотрим на поле `_missing`).
</details>

<details>
<summary>2. Как выставить TTL с джиттером</summary>

Итоговый TTL — это `baseTtl` плюс случайная добавка, равномерно распределённая на отрезке
`[0, maxJitter]` (в миллисекундах, оба конца отрезка допустимы). У `RandomGenerator` есть методы,
которые сразу дают случайное число в заданном диапазоне — выбирайте границы аккуратно, чтобы
верхний конец `maxJitter` тоже мог выпасть, а не только значения строго меньше него. TTL нужно
выставлять в миллисекундах, а не в секундах — при округлении до секунды смысл джиттера теряется.
Подробнее про `EXPIRE`/`PEXPIRE` и проблему одновременного истечения TTL —
[../theory/04-expiration-eviction.md](../theory/04-expiration-eviction.md).
</details>

<details>
<summary>3. Как атомарно объединить HSET и PEXPIRE</summary>

Нужен способ отправить в Redis обе команды как одно неделимое целое. Вариантов два: Lua-скрипт
(`EVAL`) — выполняется на сервере целиком и атомарно, работает на любом соединении; либо
`MULTI/EXEC`, но у него в Lettuce есть ловушка — состояние транзакции живёт на самом соединении,
и если это соединение общее для нескольких потоков (а у нас так и есть), чужая команда, отправленная
другим потоком между `multi()` и `exec()`, молча попадёт в вашу транзакцию. `MULTI/EXEC` безопасен
только на отдельном, выделенном под транзакцию соединении. Разбор обоих инструментов и этой ловушки —
[../theory/06-atomicity-scripting.md](../theory/06-atomicity-scripting.md).
</details>

<details>
<summary>4. Про сам паттерн cache-aside и негативное кэширование</summary>

Общее описание паттерна, разбор проблем «лавины промахов» и «дырявых» id (cache penetration) —
[../theory/09-patterns.md](../theory/09-patterns.md).
</details>

<details>
<summary>5. Как проверить negative caching отдельно</summary>

Хэш с единственным полем `_missing` = `"1"` — выбирайте имя поля так, чтобы оно не могло
совпасть с полем настоящей карточки товара. `get` для такой записи должен различать «это
негативный кэш» и «это нормальная карточка» — например, по наличию поля `_missing` в
возвращённой `HGETALL` карте.
</details>

## Подумайте после решения

- Что произойдёт, если два потока одновременно получат промах по одному и тому же `id` и оба
  пойдут в `ProductRepository`? Насколько это плохо и стоит ли с этим бороться (и какой ценой)?
- `RandomGenerator` в конструкторе — не `java.util.Random` жёстко, а интерфейс. Зачем это тестам,
  и как ещё это может пригодиться в продакшене?
- Если `ProductRepository` в реальности — это поход в другой сервис по сети, что нужно изменить
  в контракте `get`, чтобы не держать соединение с Redis (и вызывающий поток) заблокированным на
  время сетевого таймаута?
- Что произойдёт, если `HSET` + `PEXPIRE` объединить через `MULTI/EXEC` на соединении, общем для
  нескольких потоков (как в этом задании)? Почему Lua-скрипт (`EVAL`) этой проблемы не имеет?
