# 01. Архитектура: кольцо, токены, vnodes, gossip и snitch

**Зачем это знать backend-разработчику.** Запрос в Cassandra не «идёт в базу»: он приходит на любой узел, и тот решает, кто хранит строку и скольких соседей спросить. Перепутаете дата-центр в драйвере — клиент пойдёт в чужой регион. Не понимая кольцо, вы не объясните, почему упала нода, а кворум (quorum) жив.

> **Коротко:** Cassandra делит данные по кольцу токенов (token ring). Ключ партиции (partition key) превращается в токен (token), и владельцем становится узел, чей диапазон токенов (token range) это число покрывает. У узла несколько виртуальных диапазонов (vnode), а не один кусок кольца. Узлы узнают друг о друге через gossip, а дата-центр и стойку им сообщает snitch. Клиент обязан назвать свой локальный дата-центр: здесь это `datacenter1`.

Вывод команд ниже снят с живого `cassandra:5.0` (сервер `5.0.9`); Java сверена с API драйвера DataStax `java-driver-core` 4.19.3.

## Кольцо и токен

**На пальцах** (это аналогия, а не термин). Представьте циферблат на 2⁶⁴ делений. Каждый узел отвечает за дугу этого циферблата. «Дуга» — слово из аналогии: в Cassandra она называется **диапазон токенов** (token range), и гуглить надо именно «token range». Заказ кладут не «на сервер номер 3», а в тот диапазон, куда попала метка заказа.

**Токен** (token) — число на этом кольце (ring). Партиционер по умолчанию, **Murmur3Partitioner**, считает от ключа партиции хеш Murmur3 и получает токен в диапазоне от −2⁶³ до 2⁶³−1. Кольцо замкнуто: после самого большого токена снова идёт самый маленький. Узел владеет диапазоном от токена предыдущего узла (не включая его) до своего токена (включая его).

Один и тот же ключ всегда даёт один и тот же токен. Поэтому Cassandra не ищет строку перебором узлов: координатор смотрит в карту диапазонов и знает владельцев. Общий фон — [партиционирование](../../docs/00-foundations/05-partitioning.md).

```
cqlsh> SELECT token('room-1') FROM system.local;

 system.token('room-1')
------------------------
     -90371018330295163

cqlsh> SELECT token('room-2') FROM system.local;

 system.token('room-2')
------------------------
    1373785713807384263
```

Два похожих ключа дали токены, отстоящие почти на полтора квинтиллиона: хеш намеренно рассеивает соседние значения, чтобы `room-1`, …, `room-999` не легли одной горячей кучей. Обратная сторона — упорядоченных обходов «все чаты от A до F» кольцо не поддерживает.

`token()` показывает число, по которому выбирается диапазон, но само оно не адрес машины. Карту владения печатает `nodetool describering`, ответ по конкретному ключу — `getendpoints`:

```
$ nodetool describering guide
	TokenRange(start_token:-1023698561996795810, end_token:754935738826791318,
	           endpoints:[172.17.0.4],
	           endpoint_details:[EndpointDetails(host:172.17.0.4, datacenter:datacenter1, rack:rack1)])

$ nodetool getendpoints guide messages_by_chat room-1
172.17.0.4
```

Токен `room-1` (−90 371 018 330 295 163) больше −1 023 698 561 996 795 810 и не больше 754 935 738 826 791 318, то есть лежит ровно в напечатанном диапазоне. На кластере `getendpoints` напечатает столько адресов, каков RF.

```mermaid
flowchart LR
    K["Ключ партиции (partition key) chat_id"] --> H["Murmur3Partitioner"]
    H --> T["Токен (token) на кольце"]
    T --> O["Узел, чей диапазон токенов содержит токен"]
    O --> R["Следующие реплики по стратегии"]
```

## Виртуальные узлы

**На пальцах** (аналогия). Если у каждой машины один диапазон токенов (token range), добавление сервера заставляет соседа отдать половину своего диапазона. Пока данные переезжают, этот сосед один тащит и старую нагрузку, и стриминг. Виртуальные узлы нарезают кольцо на много коротких диапазонов токенов и раздают их всем машинам, как колоду карт.

**Vnode** (virtual node) — один диапазон токенов, которым владеет физический узел; таких диапазонов у узла несколько. Параметр `num_tokens` в `cassandra.yaml` задаёт, сколько их узел берёт при входе в кластер. В 4.x и 5.0 значение по умолчанию — **16**, а не 256, как в ранних 3.x: меньше диапазонов — меньше служебных метаданных и проще стриминг.

Число диапазонов видно в `nodetool status` в колонке `Tokens`:

```
$ nodetool status
Datacenter: datacenter1
=======================
Status=Up/Down
|/ State=Normal/Leaving/Joining/Moving
--  Address     Load        Tokens  Owns (effective)  Host ID                               Rack
UN  172.17.0.4  114.72 KiB  16      100.0%            9a78282e-6841-4b61-93dc-53dc42975c98  rack1
```

Первая буква — доступность (`U`/`D`), вторая — состояние (`N` normal, `J` joining, `L` leaving, `M` moving). `Owns (effective)` учитывает RF: на одном узле это 100 %, на шести узлах с RF = 3 — около 50 % у каждого.

`nodetool ring` показывает ту же машину с другой стороны — по одной строке на каждый из 16 диапазонов:

```
$ nodetool ring
Address          Rack     Status State   Load         Owns      Token
                                                                9209699462068077023
172.17.0.4       rack1    Up     Normal  114.72 KiB   100.00%   -8501128918930580951
...
172.17.0.4       rack1    Up     Normal  114.72 KiB   100.00%   -1023698561996795810
172.17.0.4       rack1    Up     Normal  114.72 KiB   100.00%   754935738826791318
172.17.0.4       rack1    Up     Normal  114.72 KiB   100.00%   1850977639061729607
...
```

Число в первой строке (без адреса) — последний токен кольца: с ним первая строка читается как диапазон `(9209699462068077023, −8501128918930580951]`, проходящий через «склейку». Токен `room-1` принадлежит vnode `754935738826791318`, а `room-2` — следующему, `1850977639061729607`: одна машина, два разных vnode.

При выходе узла его 16 диапазонов подхватывают соседи по репликам, а не один «следующий по кольцу» сервер; при входе новый узел забирает по куску у многих. Отсюда и масштабирование добавлением машин без ручного пересчёта «шарда номер N».

## Как узел выбирает свои токены

**На пальцах** (аналогия). Шестнадцать случайных точек на циферблате редко ложатся ровно: где-то две рядом, где-то пустая четверть. Поэтому у Cassandra есть «распределяющий» режим: новый узел не тянет номерки наугад, а считает, где кольцо перекошено, и забирает токены именно там.

Параметр `allocate_tokens_for_local_replication_factor` включает этот алгоритм. В образе `cassandra:5.0` он уже прописан:

```
$ grep -nE "^#? ?(num_tokens|allocate_tokens)" /etc/cassandra/cassandra.yaml
42:num_tokens: 16
55:# allocate_tokens_for_keyspace: KEYSPACE
59:allocate_tokens_for_local_replication_factor: 3
```

Комментарий рядом говорит дословно: алгоритм «пытается выбрать токены так, чтобы оптимизировать реплицированную нагрузку на узлы дата-центра», и работает только с Murmur3Partitioner. Вариантов два:

| Параметр | Откуда берётся RF | Когда брать |
|---|---|---|
| `allocate_tokens_for_local_replication_factor: 3` | указан числом | кластер только создаётся |
| `allocate_tokens_for_keyspace: guide` | из стратегии этого keyspace | keyspace уже есть |

Почему это важно на числах. При `num_tokens: 16` и шести узлах на кольце 96 точек; случайная раскладка даёт разброс владения порядка ±15–20 %, и узел с «везучими» токенами получает больше данных, больше запросов и первым упирается в диск. Алгоритм выделения сводит разброс к единицам процентов — поэтому 256 токенов, которыми раньше сглаживали случайность, стали не нужны и дефолт упал до 16. Если оба параметра пусты, токены берутся случайно (поведение 2.x/3.x), и «перекос на 20 %» в таком кластере не баг.

## Кто хранит реплики

**На пальцах** (аналогия). Важную папку кладут не в один шкаф, а в три — и желательно в три разных комнаты, а не на три полки одного шкафа: комнату может затопить. «Комната» здесь — **стойка** (rack): группа машин с общим питанием и коммутатором, которая выходит из строя целиком.

**Фактор репликации** (replication factor, RF) — сколько копий каждой партиции хранит кластер. Его задают на **пространство ключей** (keyspace), которое здесь называется `guide`. Стратегия говорит, *как* выбирать эти копии.

- **SimpleStrategy** раскладывает реплики по кольцу подряд, без учёта стоек. В репозитории она стоит на одном узле (`RF = 1`) и на учебном кластере задания 07 (`RF = 3`). Для мульти-дата-центра не подходит.
- **NetworkTopologyStrategy** задаёт RF отдельно на каждый дата-центр и старается класть следующие реплики в разные стойки (rack). Первая реплика — узел, владеющий токеном; дальше обход пропускает узлы той же стойки, пока стойки не кончились.

Сервер проверяет имена дата-центров буквально и ругается на незнакомое:

```
cqlsh> CREATE KEYSPACE nts_probe WITH replication = {'class':'NetworkTopologyStrategy','dc1':3};
ConfigurationException: Unrecognized strategy option {dc1} passed to NetworkTopologyStrategy for keyspace nts_probe

cqlsh> CREATE KEYSPACE nts_probe WITH replication = {'class':'NetworkTopologyStrategy','datacenter1':3};
Warnings :
Your replication factor 3 for keyspace nts_probe is higher than the number of nodes 1 for datacenter datacenter1
```

Разница важна: чужое имя дата-центра — **ошибка**, а RF больше числа узлов — только **предупреждение**. Keyspace создастся, запись с `ONE` пройдёт, а `QUORUM` упадёт по `UnavailableException`: двух реплик из трёх не существует.

**Разбор обхода: 6 узлов, 2 стойки, RF = 3.** Кольцо обходится в порядке n1 → … → n6, токен партиции попал в диапазон n1. Алгоритм принимает узел, если его стойка ещё не использована; узел из занятой стойки откладывается в список «пропущенных». Когда все стойки встретились, реплики добираются подряд, сначала из этого списка.

Раскладка A — стойки чередуются (n1, n3, n5 в `rack1`; n2, n4, n6 в `rack2`):

| Шаг | Узел | Стойка | Решение |
|---|---|---|---|
| 1 | n1 | rack1 | реплика 1, стойка rack1 занята |
| 2 | n2 | rack2 | реплика 2, встретились обе стойки |
| 3 | n3 | rack1 | реплика 3 — стоек больше нет, берём подряд |

Итог: `{n1, n2, n3}` — **две копии в rack1 и одна в rack2**. Потеря `rack1` оставляет одну живую реплику из трёх: `QUORUM` по этой партиции недоступен.

Раскладка B — стойки сплошные (n1, n2, n3 в `rack1`; n4, n5, n6 в `rack2`):

| Шаг | Узел | Стойка | Решение |
|---|---|---|---|
| 1 | n1 | rack1 | реплика 1 |
| 2–3 | n2, n3 | rack1 | стойка занята → в список пропущенных |
| 4 | n4 | rack2 | реплика 2, встретились обе стойки → добираем из пропущенных |
| 5 | n2 (из списка) | rack1 | реплика 3 |

Итог: `{n1, n4, n2}`. Узел n3 не стал репликой вообще, зато n2 получил копию, хотя обход прошёл его «мимо». Соотношение то же: 2 копии в rack1, 1 в rack2.

Вывод один: **RF = 3 при двух стойках не переживает падения стойки**. Чтобы потеря стойки съедала ровно одну реплику из трёх, стоек должно быть три и узлы должны делиться между ними ровно. Проверять расстановку надо командой `nodetool getendpoints`, а не на схеме.

Потеря одной реплики при RF = 3 не делает данные недоступными: две копии живы. Какое чтение их дождётся — в [06](06-consistency-repair.md), идея кворума — в [репликации](../../docs/00-foundations/04-replication.md).

## Gossip и детектор отказов

**На пальцах.** Узлы не держат общее собрание. Каждый **узел** раз в секунду болтает с парой соседей и пересказывает, что слышал: «узел C жив, поколение 4, heartbeat 900». Слух расходится за несколько раундов.

**Gossip** — протокол распространения состояния членства. Сообщение несёт **поколение** (generation, растёт при перезапуске) и heartbeat. **Seed** — узел, чей адрес прописан заранее, чтобы новичок вообще кого-то нашёл; по данным он не особенный. В задании 07 второй и третий контейнеры получают `CASSANDRA_SEEDS=cassandra-1`.

Что именно разносится, видно командой `nodetool gossipinfo`:

```
$ nodetool gossipinfo
/172.17.0.4
  generation:1791379942
  heartbeat:308
  STATUS:74:NORMAL,-1023698561996795810
  SCHEMA:293:74fd49bb-d1f6-31b7-877d-abd73128584c
  DC:8:datacenter1
  RACK:10:rack1
  RELEASE_VERSION:5:5.0.9
  SSTABLE_VERSIONS:6:big-nb
  TOKENS:72:<hidden>
```

`generation` — время старта процесса в секундах Unix: перезапуск даст большее число, и слухи старого поколения проиграют. `heartbeat` — счётчик, растущий каждую секунду. Числа после имени поля (`DC:8`, `SCHEMA:293`) — версии поля: сосед запрашивает только устаревшие у него, поэтому состояние не пересылается целиком. Узлы обмениваются дата-центром, стойкой, версией схемы и формата SSTable — и **никогда** данными партиций.

**Детектор отказов по φ** (phi accrual failure detector) не говорит «мертв после трёх пропущенных пингов». Он копит историю интервалов между heartbeat и выдаёт число φ: насколько текущая тишина нетипична по сравнению с этой историей. Порог задан в `cassandra.yaml`:

```
# phi value that must be reached for a host to be marked down.
# most users should never need to adjust this.
# phi_convict_threshold: 8
```

Значение по умолчанию — **8**: примерно «вероятность того, что живой узел молчал бы так долго, порядка 10⁻⁸». На канале с heartbeat раз в секунду это около десяти секунд тишины; на дёрганой сети детектор сам поднимает планку, потому что «нетипично» считается от истории *этого* канала. Порог 5–6 ускоряет реакцию ценой ложных `DN` при всплесках GC, 10–12 — наоборот.

При высоком φ узел считают недоступным для запросов (`DN` в `nodetool status`), но gossip ещё какое-то время пытается до него достучаться. Поэтому «нода down» и «процесс убит» — не одно и то же мгновение.

## Snitch и дата-центр

**На пальцах** (аналогия). Курьеру мало адреса получателя: нужна карта, чтобы понять, какие адреса в его городе, а какие — в другом. Snitch и есть такая карта: он не хранит данные, а отвечает «это свой город (дата-центр) и свой двор (стойка)» или «это другой регион».

**Snitch** отвечает на вопрос «в каком дата-центре и в какой стойке этот узел». От ответа зависят и расстановка реплик NetworkTopologyStrategy, и то, какие узлы драйвер считает локальными. Что настроено, печатает `nodetool describecluster`:

```
$ nodetool describecluster
Cluster Information:
	Name: Test Cluster
	Snitch: org.apache.cassandra.locator.SimpleSnitch
	DynamicEndPointSnitch: enabled
	Partitioner: org.apache.cassandra.dht.Murmur3Partitioner
Data Centers:
	datacenter1 #Nodes: 1 #Down: 0
```

Вывод снят с «голого» контейнера без переменных окружения — отсюда `SimpleSnitch`; в compose-файле репозитория snitch переопределён. `DynamicEndPointSnitch: enabled` — обёртка, которая следит за задержками реплик и уводит чтения от подтормаживающей машины. Она включена по умолчанию и объясняет, почему два одинаковых `SELECT` подряд могут уйти на разные реплики.

**GossipingPropertyFileSnitch** читает дата-центр и стойку из локального файла (`cassandra-rackdc.properties`) и разносит их через gossip. Образ `cassandra:5.0` в `docker-compose.yml` и в тестах запускается с `CASSANDRA_DC=datacenter1` и `CASSANDRA_ENDPOINT_SNITCH=GossipingPropertyFileSnitch`. Имя `datacenter1` — не наша выдумка: у `SimpleSnitch` оно зашито в коде, и тот же `cassandra-rackdc.properties` из коробки содержит `dc=datacenter1`. Переменную передают явно, чтобы значение не потерялось при смене snitch. Драйвер обязан повторить его в `withLocalDatacenter("datacenter1")`.

Облачные snitch читают регион и зону у провайдера. Менять snitch на живом кластере без плана нельзя: изменится представление о стойках, а с ним — куда класть реплики.

## Вход и выход узла

**На пальцах** (аналогия). Новый сотрудник не получает «половину стола соседа»: ему раздают по несколько папок у каждого из коллег, причём он сначала копирует их себе и только потом начинает по ним отвечать. Увольняющийся поступает наоборот — сперва раздаёт папки, потом сдаёт пропуск.

**Bootstrap** (bootstrap, ввод узла) — вход нового узла в кластер. По шагам:

1. Узел находит seed и через gossip узнаёт топологию и схему.
2. Выбирает `num_tokens` токенов — случайно или алгоритмом `allocate_tokens_for_local_replication_factor`.
3. Объявляет их в gossip; в `nodetool status` это состояние `UJ`.
4. Текущие владельцы **стримят** ему данные будущих его диапазонов. Для 16 токенов это 16 диапазонов с разными источниками — поэтому vnode лучше одного большого куска.
5. Когда стриминг закончен, состояние меняется на `UN`, и только теперь узел обслуживает чтения.

Ключевая деталь: пока идёт шаг 4, **старые владельцы не выбрасывают свои копии**. Диапазон «переезжает» копированием, а убирает лишнее `nodetool cleanup` на старых узлах. Забыли `cleanup` — диск не освободится.

**Decommission** (decommission, вывод узла) — корректный выход: узел переходит в `UL` (up, leaving), раздаёт свои диапазоны будущим владельцам и выключается. На одном узле это бессмысленно, и сервер так и говорит:

```
$ nodetool decommission
nodetool: Unsupported operation: no other normal nodes in the ring; decommission would be pointless
See 'nodetool help' or 'nodetool help <command>'.
```

Ход стриминга в обе стороны показывает `nodetool netstats`:

```
$ nodetool netstats
Mode: NORMAL
Not sending any streams.
Read Repair Statistics:
Attempted: 0
Mismatch (Blocking): 0
Mismatch (Background): 0
```

`Mode: NORMAL` — спокойный узел; во время bootstrap тот же вывод покажет `Mode: JOINING` и список файлов с процентами. Запомните разницу: `decommission` раздаёт данные сам, а `nodetool removenode` применяют к **уже мёртвой** машине — данные тогда восстанавливаются с других реплик, дольше и дороже. `docker stop` без `decommission` при RF = 3 не смертелен, но диапазоны останутся недореплицированными до repair.

## Координатор

**На пальцах** (аналогия). В большой библиотеке вы подходите к любому свободному библиотекарю. Он не обязан держать вашу книгу у себя за стойкой: он знает по каталогу, в каком зале она лежит, отправляет запросы в нужные залы и отдаёт вам результат. Если вы придёте к другому библиотекарю, ответ будет тот же.

Узел, принявший запрос клиента, становится **координатором** (coordinator) этого запроса. Он не обязан хранить строку: он находит реплики, рассылает запись или чтение, собирает ответы до выбранного уровня согласованности (consistency level) и отвечает клиенту.

Поэтому «подключился к первой ноде» не значит «читаю только с неё». В кластере из задания 07 наружу опубликован только порт `cassandra-1`, а реплики координатор достаёт по внутренней сети Docker. Если драйвер попробует открыть пул на внутренний адрес 172.x, невидимый из контейнера Maven, запросы начнут отваливаться по таймауту, хотя Cassandra жива. Учебный тест поэтому переписывает адрес первого узла на проброшенный порт.

Координатор не выбирается наугад: для запроса с известным ключом партиции драйвер ставит реплики этого ключа в начало плана. Кто ответил фактически, он сообщает:

```java
Node c = session.execute(SimpleStatement.newInstance(
        "SELECT body FROM guide.messages_by_chat WHERE chat_id = ?", "room-1"))
        .getExecutionInfo().getCoordinator();
System.out.printf("%s дц=%s стойка=%s%n", c.getEndPoint(), c.getDatacenter(), c.getRack());
```

У `Node` есть ещё `getState()` и `getDistance()`. Последний и есть «свой/чужой»: `LOCAL`, `REMOTE` и `IGNORED` — к последним драйвер вообще не открывает соединений.

## Java: сессия и локальный дата-центр

**На пальцах** (аналогия). Переезжая, вы указываете в анкете свой район. Напишете район чужого города — почтальон не найдёт ни одного дома из списка, и не потому, что дома́ исчезли, а потому что ищет их не там.

Сессия драйвера 4.x обязана назвать локальный дата-центр; в репозитории это делает `DemoSessions`:

```java
return CqlSession.builder()
        .addContactPoint(new InetSocketAddress(host, port))
        .withLocalDatacenter("datacenter1")           // ровно то же имя, что у snitch
        .withConfigLoader(DriverConfigLoader.programmaticBuilder()
                .withDuration(DefaultDriverOption.REQUEST_TIMEOUT, Duration.ofSeconds(15))
                .build())
        .build();
```

**Что будет, если имя не совпадёт.** Два разных исхода, и сообщения драйвера 4.19.3 стоит узнавать по тексту.

1. Указали контактные точки и **не** назвали дата-центр — сессия не построится:

   ```
   java.lang.IllegalStateException: Since you provided explicit contact points,
   the local DC must be explicitly set (...). Current contact points are: ...
   . Current DCs in this cluster are: datacenter1
   ```

   Последняя строка — подарок: сервер сам перечислил правильные имена.

2. Назвали **чужое** имя (`withLocalDatacenter("dc1")` при `datacenter1` на сервере) — старт не падает, в лог уходит предупреждение «You specified dc1 as the local DC, but some contact points are from a different DC: datacenter1», а первый же запрос умирает, потому что локальных узлов у политики ноль: `NoNodeAvailableException: No node was available to execute the query`. Самый коварный случай: приложение поднялось, health-check «сессия создана» прошёл, а запросы не идут.

Проверить, что драйвер и сервер договорились, можно сразу после открытия сессии:

```java
try (CqlSession session = DemoSessions.open("localhost", 9042)) {
    session.getMetadata().getNodes().values().forEach(n ->
            System.out.printf("%s dc=%s rack=%s distance=%s state=%s%n",
                    n.getEndPoint(), n.getDatacenter(), n.getRack(), n.getDistance(), n.getState()));
    // /127.0.0.1:9042 dc=datacenter1 rack=rack1 distance=LOCAL state=UP

    TokenMap tokens = session.getMetadata().getTokenMap().orElseThrow();
    var key = TypeCodecs.TEXT.encode("room-1", session.getContext().getProtocolVersion());
    System.out.println(tokens.getReplicas("guide", tokens.newToken(key)));
}
```

`TokenMap.getReplicas` — драйверный аналог `nodetool getendpoints`: карта кольца живёт и на клиенте, поэтому запрос с ключом партиции летит сразу на реплику, а не через лишний узел. Узел с `distance=IGNORED` — в чужом дата-центре.

## 🔬 Глубже: владение диапазоном и несколько дата-центров

Нагрузка (`Load`) в `nodetool status` — оценка объёма, не число запросов в секунду.

Когда дата-центров несколько, NetworkTopologyStrategy хранит полный RF в каждом. Запись с `LOCAL_QUORUM` подтверждается большинством своего дата-центра и асинхронно уходит в другой, поэтому чтение из резервного региона может отставать на секунды — и это не сбой gossip. Арифметика межрегионального трафика при `{'dc_eu': 3, 'dc_us': 3}`: одна запись превращается в шесть мутаций, но через океан координатор отправляет её **один раз** — узел-посредник в чужом дата-центре сам разошлёт копии двум соседям. Благодаря этому forwarding трафик растёт как число дата-центров, а не как суммарный RF.

Поколение gossip растёт при старте процесса, и большее поколение побеждает: узел, вернувшийся после разделения сети, не «догонит» живых устаревшими слухами. Это защита от воскресшего узла, а не замена repair данных.

## Типичные ошибки и заблуждения

1. **«Координатор — это мастер.»** Мастера нет: любой узел может координировать, реплики равноправны. Ролей «primary/secondary», как в MongoDB, здесь нет.
2. **«RF = 3 значит три узла в кластере.»** RF — число копий партиции; узлов может быть тридцать. На трёх узлах с RF = 3 копия лежит на каждом, но это частный случай.
3. **«Seed хранит все данные.»** Seed только помогает войти в gossip. Выключить единственный seed после сборки кластера обычно можно; вот только новому узлу будет не у кого узнать о соседях.
4. **«Локальный дата-центр можно не указывать.»** В драйвере 4.x его указывают явно. Ошибка в имени роняет старт сессии либо даёт `NoNodeAvailableException` на первом запросе.
5. **«Две стойки — уже отказоустойчиво при RF = 3.»** Нет: обход кладёт две копии в одну из них, и падение этой стойки убивает `QUORUM`. Нужны три стойки.
6. **«Добавил узел — старые сразу освободили диск.»** Нет: диапазоны копируются, старые копии удаляет `nodetool cleanup` вручную.

## Итоги

- Ключ партиции → токен Murmur3 → диапазон токенов на кольце. Владельца проверяют `nodetool getendpoints`, в Java — `TokenMap.getReplicas`.
- В Cassandra 5.0 у узла 16 vnode; `allocate_tokens_for_local_replication_factor: 3` выравнивает их раскладку.
- SimpleStrategy не знает про стойки; для нескольких дата-центров нужна NetworkTopologyStrategy. При RF = 3 и двух стойках две копии окажутся в одной стойке.
- Gossip разносит живость, поколение, дата-центр, стойку и версию схемы — но не данные; φ-детектор с порогом `phi_convict_threshold: 8` решает, что узел недоступен.
- Bootstrap копирует диапазоны новому узлу (`UJ`), decommission раздаёт их перед выходом (`UL`); лишние копии убирает `nodetool cleanup`.
- Snitch сообщает дата-центр и стойку: здесь это `datacenter1`, и ровно это имя обязан назвать драйвер.
- Клиент говорит с координатором; копии читает уже координатор.

## Вопросы для самопроверки

1. Два разных `chat_id` могут попасть на один узел?
   <details><summary>Ответ</summary>Да. Хеш может лечь в один диапазон, а у узла ещё и несколько диапазонов. В примере выше `room-1` и `room-2` легли в два разных vnode одной машины.</details>
2. Зачем `num_tokens` больше единицы?
   <details><summary>Ответ</summary>Чтобы при добавлении и удалении узла стриминг и нагрузка распределялись по многим соседям, а не по одному владельцу соседнего диапазона.</details>
3. Чем seed отличается от реплики?
   <details><summary>Ответ</summary>Seed — адрес для входа в gossip. Реплика — узел, хранящий копию конкретной партиции. Один узел может быть и тем и другим, но это разные роли.</details>
4. Почему в тестах указан `GossipingPropertyFileSnitch`, а не значение по умолчанию образа?
   <details><summary>Ответ</summary>Чтобы дата-центр узла был `datacenter1` и совпал с `withLocalDatacenter`. Голый контейнер показывает `Snitch: ...SimpleSnitch`, который имя дата-центра берёт из кода, и переопределить его нельзя.</details>
5. Узел `DN` в `nodetool status`. Клиент с `QUORUM` и RF = 3 обязательно получит ошибку?
   <details><summary>Ответ</summary>Нет, если живы две другие реплики нужной партиции. `ALL` при этом уже не соберётся. Подробности — в файле про согласованность.</details>
6. Шесть узлов, две стойки по три, RF = 3. Сколько реплик останется, если упадёт стойка?
   <details><summary>Ответ</summary>Одна или две — смотря в какой стойке оказались две копии этой партиции. Для части партиций останется одна реплика из трёх, и `QUORUM` по ним недоступен. Три стойки гарантировали бы ровно две выживших копии.</details>
7. Сессия создалась, а любой запрос падает с `NoNodeAvailableException`. С чего начать?
   <details><summary>Ответ</summary>С имени локального дата-центра: сравнить `withLocalDatacenter` с выводом `nodetool describecluster` и поискать в логе предупреждение «You specified … as the local DC». Второй кандидат — `getDistance()` узлов: если все `IGNORED`, политика балансировки считает их чужими.</details>
