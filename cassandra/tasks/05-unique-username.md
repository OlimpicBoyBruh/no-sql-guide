# Задание 05. Уникальный username через LWT ★★

**Бизнес-контекст:** при регистрации имя `ann` может занять только один человек. В день рассылки
сервис принимает около 300 регистраций в секунду, и на популярные имена вроде `ann` в ту же секунду
претендуют несколько человек. Обычная вставка в Cassandra — «кто последний, тот и записал»: второй
молча затрёт первого. Условная вставка `IF NOT EXISTS` согласует попытку через Paxos и говорит,
применилась она или имя уже занято.

## Что нужно сделать

- Таблица `guide.usernames`. Ключ — `username`. Колонка — `user_id`.
- `claim` вставляет пару, только если такого имени ещё нет. Возвращает `true`, если вставка
  прошла, и `false`, если имя уже занято. Занятое имя не перезаписывается.
- `claim` задаёт запросу оба уровня согласованности явно: обычный — `LOCAL_QUORUM`, serial — `LOCAL_SERIAL`.
  Тесты это не проверяют, но у условной записи их два, и оба стоит выбирать осознанно.
- `owner` читает владельца обычным чтением, без условной операции. Неизвестное имя — пустой `Optional`.
- Не ловите «уникальность» исключением: отказ — это нормальный ответ запроса.

## API

```java
public final class Usernames {
    public Usernames(CqlSession session);

    void ensureSchema();
    boolean claim(String username, UUID userId);
    Optional<UUID> owner(String username);
}
```

`ensureSchema` вызывают один раз, до остальных методов: он создаёт таблицы и готовит запросы, без него остальные методы упадут с `NullPointerException`.

- `firstClaimWins` — первое занятие имени успешно, владелец тот, кого записали.
- `secondClaimDoesNotReplaceTheOwner` — вторая попытка возвращает `false`, владелец прежний.
- `unknownNameIsEmpty` — у свободного имени нет владельца.

## Подсказки

<details>
<summary>1. Условие — часть вставки</summary>

«Записать, только если ключа нет» выражается условием на `INSERT`, а не проверкой `SELECT`
перед записью. Между чтением и записью без условия успеет вклиниться второй клиент.
Как устроена условная запись — в разделе [«Условная запись»](../theory/08-lwt-batches-counters.md#условная-запись).
</details>

<details>
<summary>2. Отказ — не ошибка</summary>

Запрос завершается успешно и в том случае, когда условие не выполнилось. Применилась ли запись,
нужно спросить у результата отдельно. Исключения здесь не будет.
</details>

<details>
<summary>3. Чтение владельца обычное</summary>

Узнать, кто занял имя, можно без Paxos. Условная операция нужна только там, где есть гонка за запись.
</details>

<details>
<summary>4. Два уровня согласованности</summary>

У привязанного запроса (`BoundStatement`, результат `bind`) есть два разных метода: один ставит обычный
уровень, другой — serial, то есть уровень самого раунда Paxos. Если не вызвать их, сработают умолчания драйвера.
Разница описана в том же разделе теории, ближе к концу.
</details>

## Подумайте после решения

- Две таблицы хранят пользователя: по id и по username. Почему без условной вставки в таблицу имён
  один username окажется у двух людей?
- Такая вставка дороже обычной. Для какого поля в регистрации эта цена оправдана, а для счётчика
  просмотров — нет?
- Пользователь нажал «Зарегистрироваться» ещё раз с тем же `userId`, и `claim` вернул `false`,
  хотя имя уже его. Как отличить такой повтор от настоящего проигрыша, не делая второй `SELECT`?
  Подсказка: в результате проигравшей условной записи видны текущие значения колонок.
