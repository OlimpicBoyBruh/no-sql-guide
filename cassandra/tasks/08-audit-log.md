# Задание 08. Журнал аудита на Spring Data Cassandra ★

**Бизнес-контекст:** служба безопасности смотрит действия одного пользователя от новых к старым.
В системе миллионы пользователей, и на каждого за месяц приходится порядка двух тысяч событий
аудита: входы, выходы, смена настроек. Сервис записи уже вызывает репозиторий. Нужно описать сущность
так, чтобы Spring сам создал таблицу и запрос по партиции. Сортировать список в Java после `findAll`
нельзя: это чтение всей таблицы.

На заготовке методы сервиса уже написаны. Тесты падают из-за маппинга, а не из-за `TODO` в теле метода.

## Что нужно сделать

- Таблица `guide.audit_events`.
- Ключ: `userId` — партиция, `occurredAt` — clustering по убыванию.
- Поле `action`.
- Репозиторий читает события одного пользователя. Метод назван от свойства ключа `key.userId`.
- `record` сохраняет событие. `byUser` возвращает события этого пользователя от новых к старым.
  Порядок даёт таблица.

## API

```java
public class AuditLog {
    public AuditLog(AuditEventRepository repository);

    void record(String userId, Instant occurredAt, String action);
    List<AuditEvent> byUser(String userId);
}
```

## Подсказки

<details>
<summary>1. Ключ из двух частей — отдельный тип</summary>

Партиция и clustering вместе образуют первичный ключ. В Spring Data для такого ключа заводят отдельный
класс и ссылаются на него из сущности. Поле времени помечают как clustering и задают убывание там,
а не вызовом `sorted()` после чтения. Форма сущности разобрана в разделе
[«Spring Data Cassandra»](../theory/10-java-driver.md#spring-data-cassandra).
</details>

<details>
<summary>2. Имя метода — это путь к полю</summary>

Репозиторий не угадывает «найди по пользователю», пока метод не называет свойство ключа.
Обход `findAll` и фильтр в памяти читает чужие партиции.
</details>

<details>
<summary>3. Умолчания фреймворка тоже решают</summary>

Два умолчания Spring Data Cassandra 5.1.1 легко принять за «и так сработает». Первое: имена колонок
берутся из имён свойств как есть, и snake_case сам не включается. Без явного имени в аннотации
колонка для `userId` будет называться `userid`, а не `user_id`: `NamingStrategy` по умолчанию отдаёт имя свойства как есть.
Второе: свойство `spring.cassandra.schema-action` со значением `CREATE_IF_NOT_EXISTS` создаёт таблицу один раз
и больше её не меняет. Если таблица уже появилась из сущности без убывания, она останется с порядком
по возрастанию, а правка аннотации её не перестроит: тест молча упадёт на сравнении порядка событий.
Сверьтесь с разделом [«Spring Data Cassandra»](../theory/10-java-driver.md#spring-data-cassandra).
</details>
